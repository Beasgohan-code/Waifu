# SUMMON architecture

## Scope and lifecycle

This checkout started with only a README. The current branch is an independent implementation, not a patch to the legacy reference, and does not import its bot implementation or data. The API (`summon/api`) and bot (`summon/bot`) are separate processes sharing **one dedicated MongoDB database**. Each process creates one native PyMongo `AsyncMongoClient` for its event loop, pings the database, checks transaction topology, installs/updates validators and indexes, and closes its client on shutdown. Schema initialization makes changes: point it only at an explicitly authorized dedicated database, not a legacy database.

The read-only topology check accepts a writable replica-set primary, mongos, or an explicitly configured load-balanced client, with sessions and the installed driver's minimum wire version. It tries legacy `isMaster` only when `hello` returns MongoDB's explicit unknown-command error. Standalones and detected unsupported configurations fail before schema changes; `/health/ready` repeats the ping and topology check. Preview/injected readiness responses are labeled and do not check a database. This is only a necessary precondition: it does not execute a transaction, test rights, guarantee majority availability or verify failover. Actual deployments and load-balanced behavior remain untested.

Snapshot-read / majority-write transactions protect claims, daily rewards, character edits plus their audit events, group settings, notes and auto replies plus audit events, trades and gifts. A replica set or sharded cluster is required; there is no non-transactional ownership fallback. Transaction callbacks may be retried by PyMongo: IDs/timestamps are prepared outside them and no Telegram sends occur inside. Selected races and rollbacks pass against a disposable single-member MongoDB replica set in CI; that does not verify every transaction, production contention or multi-node failover.

## One Telegram ingress

```
Telegram updates ──► aiogram polling / one Dispatcher ──► domain services ──► MongoDB
                            │                                    │
                            └── Bot API sends                     └── transactions
Optional Wzgram (no_updates=True, in-memory, no handlers) ──► outbound rich sends only
Telegram Mini App ──► same-origin FastAPI ──► services / MongoDB + live Telegram permission checks
```

Run exactly one aiogram poller per token. Startup removes an existing webhook without dropping queued updates; never operate a second poller or an independent webhook against that token. API workers do not consume updates and can be scaled separately. Wzgram is an MTProto client and does not register handlers or consume updates here. It is pinned and checked at startup to reject conflicting Pyrogram/Kurigram distributions and incompatible signatures. `SUMMON_RICH_ENABLED` controls that optional connection, not aiogram ingress.

The optional polling monitor observes only successful `getUpdates` responses through the existing session middleware, including empty polls. A coalescing background task stores an HMAC-derived key and the original event time, with server-time future-skew rejection and monotonic maximum updates; it never starts another poller or blocks on a Mongo write in the update callback. The API-only secret protects a bounded majority read on `/health/poller`. This is last-observed progress, not a lock, live-process proof, end-to-end health or a web restart check. Clock, replication, failure and security boundaries are detailed in [POLLING_MONITORING.md](POLLING_MONITORING.md).

## Presentation and delivery

`summon/bot/presentation.py` escapes user content, uses the attributed adapted Richgram heading/table/details builders, and emits Telegram Rich HTML (`tg-emoji`, `bordered`, `compact`). Native aiogram `sendRichMessage` is enabled by default and can carry native inline keyboards, preserving callback data. If the optional Wzgram sender is active, cards without keyboards use its `rich_text` argument; keyboard cards stay on the Bot API path because Wzgram and aiogram have different keyboard types. Definite Telegram bad-request rejections may fall back to ordinary HTML/Unicode while preserving actions. Ambiguous network failures are never retried as an additional message.

Personal group commands (`/collection`, `/profile`, `/daily`, `/manage`) are registered as ephemeral in the group menu when supported. Responses pass the incoming ephemeral ID when available; otherwise Telegram may require the bot to be an administrator. Definite rejection falls back to a DM. If the DM is forbidden, only a generic prompt is public, never private content. Telegram does **not** guarantee delivery of an accepted ephemeral message; success is not proof of receipt. Ordinary command input, moderation actions and public catch/trade/gift events are not all ephemeral. Actual Telegram client compatibility, callback behavior and custom-emoji entitlement remain unverified.

## Fair selection and state

Group settings control activity thresholds, cooldown and lifetime. Per-member activity is rate-limited, and reservation of an active spawn is transactional. For a stable active catalogue, selection first weights rarity buckets (common 55, rare 25, epic 15, legendary 5), redraws among remaining buckets when one is empty, then draws a uniform integer offset from the chosen bucket ordered by `_id`. The retained legacy `random_key` is **not** used for selection. Counting and skipping can scan O(bucket size) index entries; benchmark large catalogues before scaling. Concurrent catalogue edits between count and selection can affect exact probabilities; a missing offset is retried a bounded number of times. A snapshot-consistent sampler and replica-set load/race tests remain release work.

An active answer is stored server-side and excluded from public group responses. Guess/catch, ownership and history are persisted rather than process-local. A spawn must include its artwork: if a local `/art/` path has no public Mini App origin, or Telegram definitely rejects the photo, the matching reservation is cancelled and marked `delivery_failed` rather than posting an unguessable text-only challenge. A definite custom-emoji/caption-parse rejection first retries the same photo once with a Unicode caption. An ambiguous network failure is not retried or cancelled because the photo may have arrived; the reservation expires normally and operators should investigate. Cancellation and history changes share a Mongo transaction; a history mismatch aborts it. A synthetic history-mismatch rollback passes against the single-member CI replica set; real Telegram delivery, production failover and broader failure scenarios still need testing. Trade/gift expiry is checked server-side on acceptance; history computes elapsed pending offers as `expired` without TTL-deleting records. Offers do not reserve ownership: acceptance rechecks inventory.

## Group-protection coverage

The sole aiogram router runs protection middleware **before** message handlers, so delivered group commands and ordinary member messages are both inspected. It subscribes to edited-message updates and checks their text, captions and ordinary Telegram entities for link, keyword and mention signals. Edits never run commands, increment flood/duplicate counters, or count as new spawn activity. Newly delivered messages use shared, bounded flood/duplicate buckets; recognized commands are protected but do not advance spawn activity. Service events, bot messages and messages sent as a channel or anonymous `sender_chat` are excluded because they are not attributable to a verifiable human member. Ephemeral inputs are not counted or deleted as ordinary chat messages; flagged inputs are suppressed.

On a possible violation, the current sender role is fetched; administrators and owners are exempt. For a non-admin, the bot's current delete permission is checked before attempting deletion. A flagged handler is not run when a role or delete permission cannot be verified. A `spam_removed` audit event is recorded only after Telegram confirms deletion; ambiguous network results are not retried. Telegram and the audit store cannot share a transaction, so a confirmed deletion can still lack an audit record if storage fails. Rules cannot inspect updates Telegram did not deliver (including restrictions from privacy mode or insufficient rights), and the content filters do not recursively inspect rich-message blocks or every future message type. Test actual event delivery, permissions, edit age limits, bypasses and throughput in a dedicated Telegram group before relying on these controls.

An optional goodbye message handles delivered `left_chat_member` service events separately; it is off by default, skips bots, and can also fire when a member is removed, not only when they leave voluntarily. Its bounded Mongo fixed windows allow at most one notice per member and ten per group per 60-second bucket; limits are not sliding and can straddle bucket boundaries. The Mini App requires a current `can_change_info` right to update the setting. Older group documents missing the new fields default to disabled without a migration. Neither goodbye events nor bot replies advance spawn activity. Live Telegram service-event delivery and rate-limit behavior remain unverified.

## Trust boundaries

1. The browser is untrusted. Server-side HMAC validates Telegram `initData`, timestamp, unique fields and signed user; a SHA-256 hash of the launch signature is consumed once in MongoDB with majority write concern. The client computes the same fingerprint with Web Crypto and keeps it in page memory; `X-Summon-Launch` accompanies API requests. It is a binding identifier, **not** an identity or an authentication credential by itself. The server requires a matching, expiring HttpOnly SameSite=Strict signed cookie and a live server-side session on every protected request. Mutations additionally require `X-Summon-Request: 1` and reject a supplied unapproved Origin. Never treat `initDataUnsafe`, the binding header, callback data or a client-supplied actor ID as authority.
2. API actions use the session actor; trade/gift callbacks use Telegram's callback actor. Group management re-fetches the actor's Telegram role and applicable right for each operation. Telegram moderation and warning issuance also check current bot rights and refuse administrators, self and bot targets. Warning review/revocation are separate database corrections: they require the actor's current restrict right but can correct old warnings even if the target has since become an admin, and they do not require bot restriction rights. Saved group/admin links provide discovery, not authorization.
3. Catalogue operators are a server-side environment allowlist, never a frontend secret. Their identity is recorded with the catalogue edit in the same Mongo transaction. The API exposes no token or Mongo URI.
4. API mutation/auth rate limits use shared Mongo fixed windows; reads still require proxy-level abuse protection. Group protection uses bounded TTL buckets and the delivery/coverage limitations above. Proxies must enforce host restrictions, body limits, TLS and correctly trusted client/scheme headers. No framework default is a substitute for proxy hardening.
5. Telegram moderation and the Mongo audit write cannot be one transaction. A Telegram operation can succeed even if audit storage fails; this is a partial/uncertain outcome requiring operator review, **not** an automatic retry. Kick itself is ban then unban and can similarly be partial.

### Warning review and corrections

A current administrator with `can_restrict_members` can review a member's active warnings via the Mini App/API or reply `/warnings` in the group. Each page and correction rechecks the role with Telegram; access is scoped to the specified group and member. The actor comes from the verified session or Telegram update, not request data. The group activity API omits moderation entries for admins without restrict rights. Bot responses request ephemeral/private delivery, but the command text itself can be visible and Telegram does not guarantee ephemeral delivery.

The Mini App requires an explicit confirmation and `/unwarn` requires the literal `confirm`; a directly submitted API request is authorized by session, CSRF and current rights rather than a separate server-side confirmation challenge. Revocation soft-updates the matching active record and appends an audit event in the same transaction, with no Telegram membership action or automatic warning escalation. The driver may safely retry a transaction callback using a stable audit ID, but the application/UI does not automatically repeat an uncertain correction. The Mini App clears stale results when the group or member changes and after an uncertain mutation; subsequent review is manual. Pagination and counts are not a cross-request snapshot. Telegram permission checks and the database transaction cannot be atomic with one another, so a role may change between a successful lookup and the database action; test this and define an operational policy before release. Previously displayed information cannot be recalled after a role changes.

### Public group notes

Notes are deliberately **public text**, not a private knowledge base. A human group member requests `/notes` or `/note <name>`; SUMMON asks Telegram for current membership each time, then posts an escaped standard HTML card into the same group. Anyone who can see that message can copy or share it. Telegram only guarantees `getChatMember` for other users when the bot is an administrator; failed lookups fail closed. Admin-only `/savenote`, `/noteinfo`, `/editnote` and `/delnote`, and the Mini App/API, recheck `can_change_info`. Responses to admin commands request private/ephemeral delivery, but typed commands may be public and ephemeral delivery is not guaranteed. No rich-template expansion, automatic filters or attachments are implemented.

`GET /api/groups/{group_id}/notes` returns at most 30 notes to a currently authorized admin. `PUT /api/groups/{group_id}/notes/{name}` requires explicit `expected_revision: null` for creation or the loaded revision for an edit; `POST .../notes/{name}/delete` requires the loaded revision. Requests use verified session identity, CSRF/Origin checks, name/text bounds and shared fixed-window rate limits. The Mini App and bot require a deliberate delete confirmation, while direct API calls rely on the session, CSRF, current role and revision rather than a separate confirmation challenge. Revisions are concurrency tokens, not credentials.

Each group stores the bounded note map in its own `groups` document. Snapshot-read transactions write that document and a content-free activity event together; all writes to the group document, including message counters, can contend and be retried. Concurrent creation/edit/delete is designed to reject stale revisions and enforce the cap; selected real-Mongo race and rollback cases pass on a disposable single-member replica set. Failover, high-volume group contention and Telegram role changes remain unverified. A Telegram role check and MongoDB transaction cannot be atomic. On a conflict or uncertain write, the UI keeps a copyable in-memory draft and requires a reload; a submitted request is not automatically repeated. Navigation and browser-close guards are best effort, and drafts are not durable. Note deletion is not reversible in the app or audit feed.

### Public auto replies

The Mini App's **Groups → Auto replies** manages a separate, bounded map of public plain-text replies; it does not modify notes. An administrator's current `can_change_info` is checked through Telegram on every list, save and delete. API identity comes from the bound session, writes require CSRF/Origin checks, and create/update/delete use explicit absence/revision conditions and transactionally write a metadata-only audit event. Permission checks and the database transaction cannot be atomic. UI creation starts disabled; the server requires an explicit boolean. A direct API deletion does not have a separate confirmation challenge, though the Mini App asks for confirmation. Preview rules are fictional and writes are disabled.

Only delivered, new, human-written group text that passed protection is eligible: no bot, inline/bot-authored, anonymous/channel, forwarded, edited, ephemeral or slash-command inputs. The existing protection middleware passes its already-read group snapshot to the activity handler; a rule disabled or edited concurrently can therefore still affect a message already in flight. The bot performs one exact match after Unicode NFKC/casefold/whitespace normalization, not substring, regex or template expansion. It emits escaped standard Bot API HTML in the incoming topic, including Unicode fallback on a definite emoji rejection. Telegram privacy mode and group privileges determine which ordinary messages actually reach the bot.

Matching messages use shared fixed one-minute caps of three per member and 15 per group; limits may burst across a minute boundary. A hashed per-group/message claim is persisted with majority acknowledgement for 48 hours before sending, suppressing repeated updates while present. Suppression is conservative: a failed or uncertain claim sends nothing, and an uncertain Telegram send is not retried. TTL cleanup, failover, restoration and in-flight changes mean this is **not** an exactly-once or guaranteed-delivery promise. Auto-reply failures are logged without text and do not prevent normal collection activity. The snapshot's stored rules are validated as a whole; corrupt or ambiguous data fails closed. Telegram and MongoDB are not one transaction.

### Session lifecycle and limitations

A fresh verified launch consumes its signature before issuing a cookie. The cookie includes a high-entropy session ID and launch fingerprint; it is **signed, not encrypted**, and must not be logged. MongoDB stores only a hash of that session ID, its user ID and explicit expiry. A same-launch reload can resume the existing cookie without consuming the proof again; a different launch cannot use that cookie. Switching accounts in a shared cookie jar replaces the one cookie, so an older tab fails closed and may need a fresh Telegram launch rather than operating simultaneously. Old unbound/stateless cookies are rejected. Web Crypto and HTTPS (or secure localhost for development) are required.

Each protected request checks the unique session record with primary, bounded linearizable read concern; session creation and logout use majority writes. Expiry is checked explicitly, not by waiting for TTL deletion. A successful logout removes that session record before clearing the cookie, so a copied cookie is rejected by subsequent checks; already-authorized in-flight requests are not cancelled. A storage failure returns an error rather than silently accepting or reporting logout success. `web_sessions` must remain unsharded to retain the single-document routing assumptions; MongoDB clocks, majority durability/journaling and the actual cluster configuration matter. Linearizable reads add latency and can fail when a majority is unavailable. If sign-in fails after its one-time proof was consumed, the user must reopen from Telegram. Fake/unit and synthetic-browser tests pass, as do cross-repository expiry/revocation and concurrent proof-consumption cases against a disposable single-member replica set. Multi-worker and multi-node failover, latency, revocation races and live Telegram account switching remain release gates.

## Layers and remaining scope

- `models.py`: bounded validation/normalization; `services/`: transport-independent rules.
- `repositories/`: async data access, transactions, rate limits and audit history.
- `bot/`: aiogram command/callback routing, activity filtering and presentation.
- `api/`: identity, permissions, input validation and safe response envelopes.
- `web/`: React client using relative same-origin `/api` requests. The sample-only development preview rejects mutations; production configuration forbids it.

No tested import/migration, warning escalation, CAPTCHA, join-request workflow, raid defence, scheduled announcement service, game rooms, media upload, or full feature parity is claimed. See `todo.md` for current/expected behavior and verification gaps.
