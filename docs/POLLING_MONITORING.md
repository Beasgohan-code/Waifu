# Optional external polling-progress monitor

This is an opt-in **last observed successful Telegram `getUpdates` response**, not a deployment, poller lock, synthetic Telegram delivery test or proof the bot is alive now. Empty successful long polls count. A stopped worker can still appear recent until the freshness window expires. The in-process watchdog may request a restart sooner or later; a platform supervisor must actually restart it. Neither mechanism verifies handlers, group permissions, database transactions, message delivery, lost updates, a blocked event loop, or that another poller/webhook is absent. Never start a second consumer or self-ping for monitoring.

## Configure only in an authorized isolated environment first

1. Use a new, dedicated SUMMON database and test bot. Startup already initializes validators and indexes; enabling this feature additionally creates or validates the namespaced `summon_poller_heartbeats_v1` collection and TTL index. **Do not point SUMMON at a legacy/shared database** or assume an existing collection of that name is compatible. Keep this collection unsharded and verify the intended MongoDB topology, permissions, TLS and durability. Disabling the flag stops initialization/use; it does not immediately delete existing documents or remove the collection.
2. Set `SUMMON_POLLER_HEARTBEAT_ENABLED=true` on **both** the API and the single bot worker. They need the same private bot token, session secret and database. Synchronize the bot worker and MongoDB clocks; the API machine's local clock is not used for freshness. Use separate tokens/secrets for staging and production. A changed bot token or session secret yields a different opaque key; the status remains unavailable/stale until a new successful poll is published. Rotating the session secret also invalidates existing Mini App sessions.
3. In the API's secret manager, set `SUMMON_POLLER_MONITOR_TOKEN` to a **separate**, high-entropy URL-safe value generated from at least 32 random bytes (characters `A–Z`, `a–z`, `0–9`, `_`, `-`; length 32–128). The format and non-reuse are checked, but length does not prove randomness. Never reuse the bot token, session secret or a human password. **The bot worker does not need the monitoring token.** An enabled API fails startup if its token is absent, malformed or identical to the bot token/session secret.
4. Set `SUMMON_POLLER_STATUS_MAX_AGE_SECONDS` on the API if needed: default **120**, allowed **60–900**. Select a window longer than the expected long-poll, publishing, replication and network delays, and coordinate it with the watchdog and alert thresholds. A wider window reduces false alarms but lengthens the time after a stop during which an old observation appears fresh. The bot does not publish until `getUpdates` actually succeeds.
5. Configure an **independent** monitoring service or operator-controlled probe to make an HTTPS `GET /health/poller` with the private `X-Summon-Monitor-Token` request header. It must support custom secret headers; do not place the token in a URL, browser, frontend bundle, Telegram message, shell history, screenshot or logs. Allow the header through the trusted proxy, require TLS to every relevant hop, disable header/query logging and response caching, and rate-limit/restrict access at the edge. The application uses constant-time comparison, rejects duplicate headers, does no database lookup for invalid credentials and sets `Cache-Control: no-store`. Unauthorized requests and disabled monitoring return 404. No monitor or alert is provisioned by the application.
6. Alert on missing responses, errors and sustained non-200s, with a policy suitable for brief deploys and replica lag. Test fresh, worker-stopped, Mongo-unavailable, skewed-clock and recovery cases with that **isolated test** service. Never blindly restart the web service based on this endpoint: a web restart cannot fix a stopped bot and can mask the real fault. Use `/health` for the web service's platform restart check; `/health/ready` is a separate, limited database topology check.

## Responses and limits

| Response | Meaning |
| --- | --- |
| `200 {"status":"recent_poll"}` | The database contains a sufficiently recent successful polling observation for this bot/configuration. This is not present-time liveness or delivery proof. |
| `503 {"status":"no_recent_poll"}` | No acceptable recent observation was found. This includes no successful poll, a stopped or delayed worker, changed configuration, clock skew or delayed replication. |
| `503 {"status":"unavailable"}` | Preview/injected storage or an unavailable/timed-out Mongo read; the endpoint cannot determine progress. |
| `404` | Monitoring is disabled or the required single header is missing/invalid. |

The callback records no Telegram updates or user data. The worker coalesces observations, writes at most once per 15 seconds after the prior write completes, bounds each write to three seconds and never waits for MongoDB in the polling callback. The original poll-time UTC timestamp, not the write-completion time, is retained. MongoDB's server clock is used both when rejecting a worker timestamp more than five seconds ahead and when evaluating freshness; monotonic `$max` expressions prevent a delayed older observation from overwriting a newer one. An invalid first future observation can create an expired epoch sentinel, not a fresh observation. TTL removes old rows after their one-hour expiry **eventually**, but freshness checks do not depend on TTL cleanup. The key is an HMAC of the bot token with the shared session secret, and neither raw secret is stored in the document.

Writes use primary acknowledgement (`w=1`) so monitoring problems cannot hold up polling; reads use primary/majority with bounded execution. Replication lag, write rollback, temporary primary/majority loss, clock drift or an uncertain late write can cause delays or false alarms. Clock synchronization and a trustworthy database remain assumptions; a badly skewed worker combined with a long network delay can make event time misleading. Mongo server clocks can differ during failover. This is a best-effort operational signal, not a lease, exactly-once guarantee or security attestation. Review database access: a principal allowed to modify the collection can falsify it.

Unit/fake-store tests exercise authorization, nonblocking/coalescing, old/future timestamps, cleanup and fail-closed behavior. Two isolated MongoDB tests exercise actual expressions, schema and reordered writes; they were skipped locally but passed on the disposable single-member replica set in [hosted CI](https://github.com/Beasgohan-code/Waifu/actions/runs/42243236341). They do not prove multi-node behavior. Live Telegram, the target hosting proxy, external alerts, failover, real clocks and recovery still require an authorized rehearsal; see [testing](TESTING.md) and [deployment](DEPLOYMENT.md).
