# Render deployment guide (not yet verified live)

Render can run SUMMON, but this guide is a **deployment candidate**, not a claim of a successful deployment or a production-readiness certification. No Render resources or real credentials were used to write it. Complete the [deployment](DEPLOYMENT.md), [testing](TESTING.md) and [migration/backup](MIGRATION_BACKUP.md) gates first, and rehearse with a **new test bot and isolated database**.

## Cost, uptime and one polling worker

- The included `Dockerfile` builds the Mini App and API into one same-origin image. A separate process, `summon-bot`, is the only Telegram update poller. A [Render web service](https://render.com/docs/web-services) can run the API/image; a [background worker](https://render.com/docs/service-types) can run the bot. Review current pricing **before** creating anything: workers and persistent disks are paid; MongoDB may also cost money.
- A [free web service](https://render.com/docs/free) sleeps after 15 minutes without inbound traffic and may take about a minute to wake. Render offers **no free background-worker instances**. The separately running Telegram poller does not count as inbound traffic to the web service. Use a paid web plan if the Mini App must stay available without cold starts; a free web instance is only appropriate for a demonstration with these limitations.
- There is **no self-pinging keep-alive**. A sleeping process cannot wake itself, and a ping to the web API does not prove the bot is polling. Use appropriate always-on compute and independent alerting; do not rely on a periodic ping as a 24/7 guarantee or as a substitute for monitoring.
- Render normally starts a new worker before stopping the old one on a [deploy or restart](https://render.com/docs/deploys), **even when configured for one instance**. Two aiogram pollers for the same token can conflict or interfere with updates. This project has **no distributed poller lease**. As one platform-specific safeguard, Render documents that attaching a [persistent disk](https://render.com/docs/disks) disables zero-downtime deploys for that service and prevents scaling it to multiple instances. The old instance is stopped before the replacement starts, with brief downtime. Attach a small disk to the **bot worker before it first runs** and verify that behavior in your Render account. The disk is not used as SUMMON storage and is not a database backup; it adds cost.
- The disk protects only replacements of **that one service**. Stop any old bot, local poller, second Render service, preview environment or other consumer of the same token before starting it; never share a token between staging and production. `summon-bot` deletes the token's webhook without discarding pending updates when it starts, so do not run it while another application is using a webhook. No platform safeguard here coordinates other services or accounts.

## Set up an isolated test deployment

1. Review the billable resources and Render's current plan/region/disk options. Disable automatic deployments and service/PR preview environments while testing. Select the repository and the branch containing these changes; this PR is not automatically merged into `main`. Build from the repository-root `Dockerfile` with the Docker runtime. A local build, if you have Docker, is `docker build -t summon:local .`.
2. Create a **dedicated transaction-capable MongoDB replica set or sharded cluster**, with encrypted transport, network access restricted to the service's outbound addresses where practical, a least-privilege application account, backups and an isolated database name. A standalone server is rejected. Startup creates/updates indexes and validators, including `collMod` on matching collection names: **do not point it at the reference or a shared legacy database**. Topology detection is not proof that transactions, privileges, majority writes or failover work. Review [MongoDB access and backup](MIGRATION_BACKUP.md) separately.
3. Create a Render **web service** from the Dockerfile. Its default Docker command is `summon-api`; it binds `0.0.0.0` to Render's `PORT` (otherwise 8000), serves the built Mini App and `/art/` on the same origin as `/api/`, and disables Uvicorn raw-path access logs. Configure Render's health-check path as `/health`. Use a free plan only if its sleep/cold-start behavior is acceptable; otherwise select a paid web plan.
4. In Render's private environment settings for the web service, set the variables in the table below. For `SUMMON_WEBAPP_URL`, use the **actual public HTTPS origin** shown by Render (or your own configured HTTPS domain), and enter the identical browser-serialized origin in `SUMMON_ALLOWED_ORIGINS`. The URL must have no path, query, fragment or trailing slash for the origin list. If the Render-assigned URL is not available before the first creation step, use an HTTPS URL you control temporarily, then update both variables to the assigned URL and redeploy the web service **before** creating the bot worker or inviting users. Validation only checks syntax, not reachability.
5. Once the web service is running with the final origin, create **one** paid Render background worker from the same repository, branch and Dockerfile. In its Docker command field override the image command with `summon-bot`; configure the same required variables and the same bot token, database and session secret. Attach the small persistent disk and verify the worker is limited to one instance **before** it starts. No additional `summon-bot`, webhook receiver, Wzgram update handler or staging process may use that token. API and worker run database initialization at startup; inspect privileges and logs.
6. In an authorized test environment, check `/health`, `/health/ready`, `/api/bootstrap` and the Mini App through the public HTTPS origin. The readiness response must report `ready`, not `preview`, and real requests should be tested through the actual proxy. Configure the bot's Mini App URL in BotFather; then test `/start`, a group command, permissions and a collection action with consenting test accounts. Confirm the public art URLs load. Inspect sanitized logs for polling conflicts, failed Telegram calls or database errors. Verify the web service's trusted-host, TLS, proxy/header forwarding, origin and rate-limit behavior; never log tokens, signed Telegram launch data, cookies or database URIs.
7. Exercise a worker redeploy and a simulated failure with that **test token**: confirm the old process stops before a new one starts, the worker is restarted as expected, and messages recover without a second consumer. Test a database outage and restoration, backup/isolated restore, the session revocation flow and your external alerting. Render's behavior, timing and all of these production boundaries remain unverified here. Roll out to real users only after the remaining release gates pass and the owner authorizes it.

| Environment variable | Where / purpose |
| --- | --- |
| `SUMMON_ENVIRONMENT=production` | Both services; production disallows preview. |
| `SUMMON_BOT_TOKEN` | Both; a fresh private test token. The bot worker consumes updates; the API validates launches and checks permissions. |
| `SUMMON_SESSION_SECRET` | Both; the **same** private random secret of at least 32 characters. |
| `SUMMON_MONGO_URI` | Both; the same private transaction-capable test cluster URI. Never post it in chat, logs or Git. |
| `SUMMON_MONGO_DATABASE` | Both; the same new dedicated database name. Default `summon`. |
| `SUMMON_WEBAPP_URL` | Both; the actual public HTTPS Mini App origin, for example `https://your-service.onrender.com`. |
| `SUMMON_ALLOWED_ORIGINS` | Web: JSON array containing that exact origin, e.g. `["https://your-service.onrender.com"]`. This also makes the origin explicit if a proxy presents HTTP internally. The frontend still uses same-origin URLs and cookies. |
| `SUMMON_OPERATOR_IDS` | Both; optional server-only JSON array of trusted Telegram IDs. The default is `[]`, with no operators. |
| `SUMMON_POLL_WATCHDOG_SECONDS` | Worker: optional bounded integer `120`–`3600`, default `300`. |
| `SUMMON_WEB_DIST` | The container sets `/app/web/dist`; do not point this at secrets or application source. Outside Docker it is empty by default. |
| `SUMMON_RICH_ENABLED` | Optional outbound-only Wzgram connection; default `false`. If enabled on a service, provide its Telegram application ID/hash privately. Native Bot API rich messages and premium-emoji settings are separate; see [compatibility](TELEGRAM_COMPATIBILITY.md). |

## What the health checks and watchdog actually do

- `/health` checks that the **web process** responds. Render can use its [web-service health checks](https://render.com/docs/health-checks) to restart an unresponsive web instance. `/health/ready` also pings MongoDB and checks its reported topology; use an independent monitor/alert for it. Neither endpoint checks the separate worker, Telegram delivery, transaction success or a user's ability to use the bot. A preview response is not production database readiness.
- The bot's in-process watchdog records successful **`getUpdates` responses**, including empty long polls in quiet groups. If none succeeds for the configured window, it asks aiogram to stop and exits with an error; it **does not start a replacement poller itself**. A process manager such as Render is expected to manage the failed worker; test restart behavior and alert on repeated failures. Sustained Telegram/network outages or a competing poller can also cause timeouts and restart loops.
- The watchdog runs on the bot's event loop. It cannot guarantee recovery from a fully blocked event loop or stuck shutdown, and does not verify that update handlers, MongoDB writes, permissions or outgoing messages succeed. It does not protect startup before polling begins. Use independent alerts and an authorized end-to-end test in addition to process logs. No watchdog can compensate for an unconfigured worker or guarantee 24/7 availability.
