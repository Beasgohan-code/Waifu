# SUMMON MongoDB schema and safeguards

Use a **new, dedicated database** and native PyMongo Async. Timestamps are UTC BSON dates, Telegram IDs are numeric, and character/trade/gift/spawn IDs are strings. `summon/database.py` is authoritative for validators and indexes. Startup pings MongoDB and checks for a supported transaction topology before creating missing collections, applying validators (`collMod` on existing collections), and creating indexes; it fails on errors. Initialization is a write operation and can affect an existing database. The topology check is not a real transaction or permissions test. No legacy collections have been modified by this session.

Claims, failed-spawn cancellation/history, rewards, trade/gift acceptance, group settings/notes and audit, warning issuance/revocation/audit and catalogue edits/audit use snapshot-read, majority-write transactions on a replica set or sharded cluster. No fallback disables transactions. Unit tests use fakes; selected scenarios also pass against a disposable single-member replica set in CI, not a production or highly available deployment.

Trade/gift acceptance independently checks `expires_at`; history presents pending documents whose deadline passed as `expired` at read time. It does not delete or bulk-rewrite those documents. Cancellation is limited to unexpired pending offers. For a definitely rejected or unavailable spawn image, cancellation clears only the matching `active_spawn` and marks its history `delivery_failed` in the same transaction; an inconsistent history aborts the transaction. An ambiguous network failure can leave a temporary active challenge until expiry.

### Public group notes

The optional, separately named `groups.saved_notes_v1` map contains up to 30 lower-case, ASCII-safe keys. Each record stores the public plaintext `content`, a 32-hex random `revision`, creation/update timestamps and actor IDs. Notes are group-scoped and capped at 1200 Unicode characters each; map validation and group lookup use the existing `_id` index, with a 5-second server-side read limit. The group schema declares the map optional and uses MongoDB `$jsonSchema` `maxProperties`, `patternProperties` and required fields; application validation additionally rejects whitespace-only, unsupported control and invalid Unicode text. The field is not a migration of any legacy notes. If existing data occupies this reserved field with an invalid shape, note operations fail closed rather than overwrite it; an authorized operator must investigate, not silently delete or replace it.

Creation compares against absence; edit and delete compare the exact loaded revision within a snapshot transaction. The group document update and one `note_changed` activity event (group, actor, action, note name, revision and timestamp) commit together. Audit events **do not contain note text**; deletion removes current text and cannot be undone through SUMMON. IDs used by the callback are generated before retries. This shared group-document write can conflict with concurrent activity counters or other edits; driver retries and eventual failure must be load-tested on a real replica set. Unit fakes and the single-member CI concurrency/rollback cases do not establish production-scale atomicity, failover or deployment safety. Use authorized encrypted backups and a rehearsed restore if recovery is needed.

MongoDB's official [`$jsonSchema` reference](https://www.mongodb.com/docs/manual/reference/operator/query/jsonSchema/) lists the keywords used here; wire-compatible services are not assumed to support them. Existing collections receive `validationLevel=moderate` at initialization, so validation does not retroactively repair old documents. Old app versions may reapply an older validator at startup; coordinate versions and back up before any upgrade/downgrade. Names and text are public in group messages but may still be sensitive in backups and logs.

### Public exact-match auto replies

The optional `groups.auto_replies_v1` map is independent of notes and legacy fields. It holds at most 20 ASCII-safe 1–32-character names. Each entry has a normalized `trigger` (2–64 Unicode code points), public plain-text `response` (1–800 code points), explicit `enabled` boolean, 32-hex revision and creation/update actor/time metadata. The server normalizes triggers with Unicode NFKC, casefolding and collapsed whitespace; it rejects slash-command triggers, controls and duplicate normalized triggers, even on disabled rules. The Mongo validator bounds the map and fields; application validation also checks normalization, uniqueness, controls and UTF-8. A malformed existing map fails closed rather than being replaced. Normal group responses omit both private storage maps, but the trigger and reply themselves must be treated as **public**, including in backups.

A create requires an absent name, an update/delete the loaded revision. Group document changes and a metadata-only `auto_reply_changed` event (group, actor, action, rule name, revision and timestamp) use the same snapshot/majority transaction. The audit does **not** deliberately include trigger or reply text; choose non-sensitive rule names as they appear in the audit. IDs are stable across transaction retries. Other group writes can contend on the same document. An uncertain commit requires reviewing current rules and audit before retrying.

After protection accepts a delivered matching message and fixed-window checks pass, the bot inserts a SHA-256-derived `once:` ID into `rate_limits` with a majority write and 5-second write-concern timeout, expiring 48 hours later. The claim contains no message text, trigger or reply and is made **before** Telegram delivery. Existing claims suppress replay attempts; an uncertain claim fails closed and a timeout after the Telegram send is not retried. TTL cleanup is asynchronous, so suppression can last longer; after cleanup, old duplicate updates may be processed again. A confirmed claim is not proof a response was delivered. Restoring, deleting or losing claim records can permit duplicates; clocks, durability, replication and TTL configuration matter. These mechanisms do not establish exactly-once delivery under all failures and must be tested on the intended topology.

### Warning corrections

Issuance inserts the warning and its `moderation` audit event in one transaction. Revocation conditionally updates the same warning by `_id`, group, target and active status, setting `revoked_at`, `revoked_by` and `revocation_reason`; a `warning_revoked` activity event with the warning ID, actor, target, reason and time is written in that transaction. The original warning and audit event are retained. A missing, already-revoked or differently scoped ID gets the same not-found response. Old SUMMON warnings with no `revoked_at` match MongoDB's null equality and remain active without a data migration. Corrections never undo an earlier Telegram ban/mute and never initiate another Telegram action.

Reads are scoped to group/member, rate-limited, sorted by `(created_at, _id)` descending and limited to 25 rows (five in the clients); cursor anchors are scoped to the same group/member and can still be used after revocation. Indexed page, anchor and exact-count operations have 5-second MongoDB server execution limits, but large counts can still be costly and network timeouts are a separate concern. Page and count reads are **not** a single snapshot: concurrent actions can change the count, remove rows, or make a page empty. Successful revocation is atomic only to the extent the real transaction deployment supports it; driver transaction/commit retries use stable event IDs, and callers must inspect state after an uncertain outcome rather than resubmit automatically. One warning race/rollback/legacy-count test passes against the disposable single-member CI replica set; production failover, scale and Telegram behavior remain unverified.

The added index is non-destructive, but older SUMMON processes still count revoked warnings and do not enforce the new activity-feed redaction. Coordinate the upgrade/cutover so old and new versions do not serve the same group concurrently; plan any downgrade and verify backups first. Treat warning reasons and actor/target IDs as sensitive moderation data, including in backups and proxy access logs.

Collection reads are scoped to the authenticated user's inventory. The optional duplicate filter requires `quantity > 1`; favorite and duplicate filters can be combined at the API. Copy sorting uses `(quantity DESC, character_id ASC)`, with a per-user index; the default first-added order uses `(acquired_at DESC, character_id ASC)`. `acquired_at` is set when the inventory row is first inserted and is not the latest copy's acquisition time; old rows may lack it. Pages and counts are separate reads, so concurrent ownership changes can alter pagination. Filtering/sorting never changes inventory. Apply the added index during a planned authorized rollout and test its cost on realistic data.

Character selection uses weighted nonempty rarity buckets and a uniformly drawn `_id` offset, not a fixed random-key pivot. Fairness is exact only for a stable bucket during the count/read; concurrent catalogue edits and large-index skip cost require additional integration/load verification. Rarity weights are application defaults, not yet group-editable.

The optional sample seeder is insert-only for `aiko`, `ren`, `mira`, using `$setOnInsert`; it does not touch inventory. Its default mode never connects. The confirmed apply path also runs normal validator/index initialization; see [deployment](DEPLOYMENT.md).

## Migration and recovery

No importer is implemented and no migration has been run. An offline, read-only preview can inspect authorized legacy JSONL exports, exact mapping manifests and an optional SUMMON inventory export; it cannot establish source completeness or migration readiness. Do not rename, drop, merge or overwrite legacy collections. Before importing legacy `anime_characters_lol`, `user_collection_lmaoooo`, group records or SQL data, make an authorized encrypted backup, inspect the actual schema, design explicit mappings for character IDs/rarities/duplicates, preserve Telegram ownership, run an isolated dry run, reconcile counts and quantities, rehearse rollback, then perform a planned cutover with writers stopped. Never dual-write stores or import tracked sessions/logs. See [migration and backup](MIGRATION_BACKUP.md) for the preview, release procedure and confirmation safeguards.
